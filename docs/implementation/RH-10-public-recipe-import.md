# RH-10 公共菜谱数据导入脚本

## 1. 一句话总结

写一个幂等的导入脚本，把上游 What-to-eat-today 仓库（其菜谱数据源自 HowToCook）的 `recipes_with_images.json` 索引 + 323 篇 Markdown 菜谱清洗、解析、去重后写入 SQLite 的 `recipes` 表（`owner_id IS NULL` = 公共菜谱），让 RH-08 的列表/搜索和 RH-07 的一键导入第一次有了真实数据。

## 2. 在项目中的位置

Day 2 收尾任务，也是「菜谱大全」的数据来源。没有它，RH-08 的列表/搜索是空转的。导入后 169 条公共菜谱进入 `recipes` 表，成为后续 Day 3 向量化、Day 4 推荐、Day 5 菜单规划的公共知识底座。

- `backend/app/services/recipe/public_import.py` —— 纯解析逻辑（md 文本 → 结构化 dict），可单测。
- `scripts/import_public_recipes.py` —— 编排脚本（读 JSON + md、去重、写库、`--reset`/`--limit`）。
- `backend/tests/test_public_import.py` —— 9 条解析单测（标题/难度/描述/食材/步骤/图片/编号列表）。
- `backend/app/models/recipe.py` —— 新增 `source` 字段（数据来源溯源）。

## 3. 实现细节

### 3.1 数据源结构

上游每个菜谱是一个 Markdown 文件，HowToCook 风格：

```
# 咖喱炒蟹的做法
{介绍段落}
预估烹饪难度：★★★★
## 必备原料和工具      → 食材名（无用量）
## 计算                → 食材 + 用量
## 操作                → 步骤（有序）
## 附加内容            → 忽略
```

另有 `recipes_with_images.json`（169 条）提供干净的元数据：`name` / `category` / `cooking_time` / `tags` / `image_url` / `file_path`（指向 md）。

### 3.2 导入流程

1. 读 `recipes_with_images.json`（索引）。
2. 逐条按 `file_path` 读 md，`parse_dish_markdown` 提取标题/描述/难度/食材/步骤。
3. 组装成 `Recipe`（`owner_id=None`、`visibility=public`）+ 子表 `ingredients`/`steps`。
4. 按 `source` 去重：已存在则跳过（幂等）。

### 3.3 清洗规则（对应 PLAN Day2 任务2）

| 规则 | 做法 |
|---|---|
| 去重 | 按 `recipes.source`（归一化后的文件路径）判重，重复运行不重复导入 |
| 统一字段 | 标题去「的做法」后缀；难度 ★→「简单/中等/困难」；食材/步骤结构化到子表 |
| 缺失字段用 null | `cuisine` 上游没有→`null`（不编造）；无难度行→`null` |
| 保留来源 | `source` 存上游文件相对路径（如 `data/dishes/aquatic/咖喱炒蟹.md`） |

### 3.4 数据质量（导入 169 条）

| 指标 | 数量 |
|---|---|
| 公共菜谱总数 | 169 |
| 有食材 | 169（100%） |
| 有步骤 | 169（100%） |
| 有难度 | 158 |
| 有描述 | 143 |

## 4. 设计决策与权衡（面试重点）

- **为什么加 `source` 字段，而不是复用 `source_recipe_id`？**
  - 两者语义不同：`source_recipe_id` 是「个人菜谱从哪个公共菜谱复制来的」（导入溯源），`source` 是「这条公共菜谱本身来自哪个上游文件」（数据溯源）。混淆会导致「公共菜谱的出处」和「个人菜谱的来源」缠在一起。`source` 同时服务授权/版权追踪（见下方授权说明）。

- **为什么解析做成「纯函数」模块，而不是全塞在脚本里？**
  - 解析是最容易出错、最需要回归测试的部分（标题后缀、难度星级、食材名/用量、步骤顺序、图片/注释噪声）。纯函数无 IO，可以像普通单元测试一样覆盖；脚本只做「读文件→调解析→写库」的编排，不好测的部分尽量薄。这延续了 RH-07 的「service 厚、壳薄」原则。

- **为什么按 `source` 判重而不是按 `title`？**
  - title 会重复（不同来源可能同名菜），也可能被清洗改动；`source`（文件路径）在单次数据源内唯一且稳定，是天然的幂等键。重复导入同一上游不会产生第二份。

- **为什么解析容忍多种列表符号（`-` / `*` / `1.`）？**
  - 上游 323 个 md 并非严格同构：有的用 `- `，有的用 `* `，有的步骤用 `1. ` 编号。若只认 `- `，约 1/4 的菜谱会丢步骤（实测从 127→169，正是补上 `*` 和 `1.` 后拉满）。数据清洗的第一性原理是「先摸清真实格式再定解析规则」，而不是假设格式统一。

- **为什么导入 169 条而不是计划里的 30--100？**
  - 计划说「以能完成检索和演示为准，别把采集变成主要工作」。上游 `recipes_with_images.json` 本身就是干净索引，169 条一次导入成本极低，还能让 Day 3 的向量检索有足够样本；不必人为砍到 100。反过来，如果数据要手工逐条清洗，那才会收敛到 30。

- **为什么不顺带做「番茄=西红柿」这类同义词归一？**
  - 这是语义/同义词问题，精确 `LIKE` 搜索解决不了（搜「番茄」找不到「西红柿炒蛋」，因为数据里写的是「西红柿」）。这属于 Day 3 向量检索 / 后续 Synonym 映射的范畴，Day 2 的确定性搜索不该越界去维护一张同义词表。

## 5. 面试高频问题 & 回答要点

**Q1：公共菜谱数据是怎么进的库？**
要点：上游 HowToCook 风格的 md + JSON 索引 → 纯函数解析（标题/描述/难度/食材/步骤）→ 组装 ORM 写 SQLite，`owner_id=NULL` 标记公共菜谱，`source` 存文件路径溯源，按 `source` 幂等去重。

**Q2：清洗时遇到格式不统一（`-`/`*`/`1.`）怎么办？**
要点：先摸清真实数据分布再定规则，解析器同时容忍无序和有序列表标记；实测只认 `-` 会丢 1/4 步骤，补上 `*` 和 `1.` 后食材/步骤 100% 覆盖。

**Q3：怎么保证重复跑导入脚本不会重复入库？**
要点：以 `source`（归一化文件路径）为幂等键，已存在则跳过；`--reset` 用 ORM 级 delete 触发子表 cascade，不留孤儿食材/步骤。

**Q4：`source` 和 `source_recipe_id` 有什么区别？**
要点：`source` 是公共菜谱的数据出处（上游文件路径，服务版权溯源）；`source_recipe_id` 是个人菜谱「从哪个公共菜谱导入」的溯源。一个是数据血缘，一个是业务导入血缘。

## 6. 踩坑

- **列表符号不一致**：上游 md 混用 `- `、`* `、`1. `。正则 `^(?:[-*+]\s+|\d+[.、)]\s*)` 统一识别无序+有序项，否则「凉拌木耳」这类全 `*` 的菜谱步骤全丢。

- **食材用量两种写法**：「肉蟹 1 只」用空格分隔，「干木耳: 20g」用冒号分隔。用 `^([^\s\d:：]+)[:：]?\s*(.*)$` 统一拆 name/quantity，并剥掉 `* 份数` 这类噪音后缀。

- **描述里混入图片和注释**：`![成品](./成品.jpg)`、`<!-- ... -->`、`> 引用` 都会污染描述。解析时跳过图片/注释/引用行，纯图片行不产生空描述（回退到 JSON description）。

- **bulk delete 不走 ORM cascade**：`db.query().delete()` 是批量删，不会触发 `recipe_ingredients`/`recipe_steps` 的 `delete-orphan` cascade，会留下孤儿子表行。`--reset` 必须用 `db.delete(recipe)` 逐条删（或手动删子表）。

- **SQLite `LIKE` 中文**：中文无大小写，`LIKE '%鸡蛋%'` 正常命中；但「番茄」搜不到「西红柿」是**同义词**问题而非 LIKE bug，别当成搜索坏了去修。

- **schema 演进与 `create_all`**：给 `recipes` 加 `source` 列后，`create_all` 不会给已存在的表 ALTER 列。开发库需要一次性的 `ALTER TABLE recipes ADD COLUMN source VARCHAR(500)`（或删库重建），这正说明「MVP 用 create_all、多人协作要上 Alembic」的边界在哪。
